Pain Points vs Solutions

单机 AI 助手的失控，
由工程级工作流终结。

告别“开局很惊艳，越写越混乱”。把软件工程的刚性纪律，无缝注入每一次人机协同。

UNMANAGED · 失控面
GOVERNED · 治理面
01

提示词修罗场

凭直觉让 AI 改代码，改动顺着调用链胡乱扩散，越修 bug 越多。

02

会话一次性与上下文断裂

关掉终端进度全部丢失，无法继承项目历史上下文，无法跨天续跑。

03

自问自答伪测试

编写代码的 Agent 自己写测试自己跑，结论永远是 pass，上线即故障。

04

宿主配置各自为政

团队换个 IDE，Hooks、MCP、指令全部推倒重来，无法标准化。

05

无对质证据链

开发者口头说“同意”，改动出了锅无法还原当初究竟达成了什么共识。

Case Studies

实战案例：
两条真实工程链路。

详细拆解真实工程中【能力面（工作流）】与【治理面（工程规则）】的端到端落地全景。

场景一 · 能力面 · 实战案例：海外商户风险拦截与鉴权重构

能力面实战 · L2 复杂任务

业务背景

新增支付前置风控拦截中间件，涉及核心网关契约、跨模块调用与高频只读库写入。通过严格工作流确保 0 故障上线。

Step 01 / 定级路由new-task

两问定级，划定触达面闭集

开发者向 AI 提出需求，Agent 触发两问排查（是否改动公共 API？是否跨 3 个以上业务文件？）。排查命中后机器硬锁定为 L2，自动在 workflow/specs/feat-payment-intercept/ 生成三件套（spec.md / tasks.md / verify-report.md）。

Step 02 / 人件门审批原话代录台账

Plan & Design 停机点原话对质

Agent 起草架构意图（Intent）后停机等待，开发者回复：

“只针对海外商户（is_intl=true）生效，超时 500ms 必须降级放行并报警，绝不能阻塞支付主流程”

Agent 将原话逐字代录进台账，未经批准坚决不推进代码实现。

Step 03 / 手术式编码tasks.md 勾选

最小 diff 实施，每行变更可溯源

进入 Build 阶段，Agent 严格根据 tasks.md 拆解的任务清单单步实现，完成一项打勾一项。严禁顺手重构相邻代码、改动无关格式或引入多余依赖。

Step 04 / 独立新会话复核Independent Review

换新会话审查，三件套凭证关单

强制新开干净会话，传入固定 git range，由独立 review 模型进行审计对质，重点攻击 500ms 超时降级用例，产出结论为 pass 的复核报告。最后运行闭环校验脚本完成规范归档。

静态三件套硬门禁核验与本地泳道大盘同步sh
$ flow-kit run check-spec-packages.mjs
✔ [spec.md] 验收标准定义完整 (4/4 契约项)
✔ [tasks.md] 6/6 任务项已全部勾选闭环
✔ [verify-report.md] 独立复核结论: pass · 关联 runId: run-202611-081
🎉 任务 feat-payment-intercept 合规归档，本地 workflow-board 自动流转至 Done 泳道。
场景二 · 治理面 · 实战案例：跨 Claude / Trae 团队中性门禁与模型角色分工

工程治理面实战 · 多宿主协同

业务背景

团队有的在终端使用 Claude Code，有的在 Trae IDE 中编码。需要在不入侵业务代码的前提下，统一实施提交前拦截、门禁墙钟预算与模型权限分工。

Step 01 / 中性规则声明gates.json

单一事实源声明拦截策略

在 .agents/hooks/gates.json 中定义全局提交门禁与权限清单：allow / deny / ask 三类条目按 shell / read / web 分类，阻断高危凭证泄露与越权目录修改。

// .agents/hooks/gates.json 中性门禁规格json
{
  "mirrorOf": ".agents/settings.json#/permissions",
  "deny": [
    { "tool": "shell", "pat": "git reset --hard",
      "reason": "禁破坏性重置" }
  ],
  "ask": [
    { "tool": "shell", "pat": "rm -rf",
      "reason": "可能递归删除文件" }
  ]
}
Step 02 / 全宿主一键编译编译器自动落盘

同源编译至 14 宿主原生规范

执行 flow-kit install 或 upgrade，规则自动编译映射为 Claude Code 的原生 hooks、Trae 原生配置和 Codex 规则。托管规则幂等更新，个人扩展安全保留。

Step 03 / 模型三角色注入model-roles.local.json

Code / Judgment / Review 精准分工

在本地配置文件中指定：编码分配高吞吐编码模型，架构意图分配强思考模型，独立复核分配严苛审计模型。安装器自动在各宿主 agent 声明中精准注入对应模型标识。

Step 04 / 体检与证明链doctor --attest

防漂移验证与安全基线留存

运行 flow-kit doctor --attest 输出带哈希签名的安装证明链。在 CI 中接入 flow-kit diff --strict，杜绝任何未备案的规则篡改与模板孤儿。

运行升级命令时，基线三方合并机制将自动保留用户的本地自定义修改，确保配置永不被覆盖冲刷。

01 安装与宿主接线 把引擎装进项目，并接到你正在用的 AI 宿主上
flow-kit install npx agentic-flow-kit install --auto-hosts --lang zh-CN 主力命令

从零装入引擎并编译到各宿主

安装器会生成 .agents/** 引擎目录、各宿主适配目录、Git 门禁、按 origin 自适应的 CI 与 devcontainer，并写入一份安装清单（manifest）记录每个托管文件的哈希。

  • --auto-hosts 自动扫描项目中已有的 AI 目录（.claude / .trae 等）并预选安装
  • --agent <host> 可重复或逗号分隔，指定要接线的宿主
  • --stack <name> 技术栈 profile：dotnet / node / typescript / rust / go / java / python / cpp / empty
  • --surface frontend|api|data 切面，可叠加
  • --tier lean|standard|enterprise 治理档位
  • --dry-run 只打印计划，不写盘
--auto-hosts--agent--stack--surface--tier--ci--hardened--model--dry-run--json--strict--baseline-only
无参数且处于交互终端时，会直接进入 TUI 向导，用方向键选择技术栈与宿主。
flow-kit add-host <host> flow-kit add-host claude --model claude:code=haiku

给已有项目补接一个新宿主

以 categories: ['host'] 重跑安装，只写新宿主那一部分文件，沿用清单里记录的栈与语言。宿主目录已存在时会报 HOST_EXISTS。

--target--model--dry-run--force--json
flow-kit remove-host <host> flow-kit remove-host trae --dry-run

摘掉一个宿主的全部接线

删除该宿主的托管文件，摘除它的 MCP / 门禁 / 权限条目与合并块，并解除用户级 hook 引用，最后重写清单。--dry-run 可以先看会删什么。

flow-kit list-hosts flow-kit list-hosts --json 14 宿主

查看内置与外部宿主的能力矩阵

列出每个宿主接线的目录、命令面、Agent 面、技能模式、门禁、权限与 MCP 支持情况。除了内置 14 个宿主，还会探测 $HOME 下未受管但已安装的宿主。

--json
flow-kit new-host <name> flow-kit new-host myhost --dir .myhost --hooks

为团队自定义一个新宿主适配

按现有宿主的骨架生成一个新的适配目录与 host-meta 定义，可选择是否带门禁、权限与 MCP 接线。

--dir--label--skills native|shared|index--hooks--permissions--mcp claude|opencode--out
02 体检、漂移与安装证明 确认装对了、没被人偷偷改过
flow-kit doctor flow-kit doctor --deep --attest --out proof.json 最常用

全面体检：钩子、配置、Git、模型、Node 版本

逐项检查安装清单、hook 接线、MCP、权限、devcontainer、模型配置与 Node.js ≥ 22，并校验证明链。

  • --deep 额外执行 check-local-gates.mjs 本地门禁扫描
  • --fix 尝试自动修复可修复项
  • --attest --out <file> 输出带哈希签名的安装证明链
--deep--fix--attest--out--json
flow-kit diff flow-kit diff --strict

只读比对当前仓库与引擎模板的漂移

把每个托管文件的哈希与清单比对，归成五类：missing（缺失）、user-modified（被你改过）、kit-updated（引擎有新版）、orphan（孤儿文件）、unchanged。全程零写盘，可直接接进 CI。

  • --strict 有未清理项时返回退出码 1
  • --all 展开列出每一项
flow-kit status flow-kit status --json

看一眼当前安装概览

输出已接线的宿主、栈、切面、档位、门禁与技能概况，适合快速确认"这个仓库到底装了什么"。

flow-kit explain <targetRel> flow-kit explain .agents/hooks/gates.json

解释某个文件为什么长这样

给出目标文件由哪条机制、哪个模板、哪个宿主规则生成，以及它的作用与关键字段。用于"这条规则从哪来的"这类追溯。

03 安装生命周期：接管、升级、清理 让引擎跟着你走，且永远不覆盖你的改动
flow-kit adopt flow-kit adopt --agent claude --dry-run

接管既有或半安装目录

把已经存在的引擎文件按哈希与语言最佳匹配纳入清单，不改写任何项目文件，只写一份清单作为后续接管基线。适合"团队里已经有人手工装过一半"的仓库。

  • 已修改文件不覆盖，先 --dry-run 检查
  • 没有任何可接管文件时返回退出码 1
flow-kit upgrade flow-kit upgrade --explain-policy

按清单重放升级到最新规则

先迁移清单 schema，再按清单里记录的宿主与栈重放一次完整安装。托管规则幂等更新，你的本地改动通过三方合并保留。

  • --explain-policy 打印本次升级策略
  • 清单里没有宿主时返回 NO_HOSTS_IN_MANIFEST
flow-kit prune flow-kit prune --dry-run

清理孤儿文件与废弃模板

删除已从引擎下线、但还残留在项目里的托管文件，并清理清单条目。只有哈希匹配的才删，你改过的文件默认保留。

--baseline--dry-run--force--strict
flow-kit uninstall flow-kit uninstall --dry-run

完整卸载引擎

删除全部托管文件与目录，摘除带标记的合并块并解除 hook 引用。根目录记忆文件与你改过的文件默认保留，除非加 --force。

flow-kit --baseline-only flow-kit install --baseline-only

只重建基线，不重装

新 clone 或执行过 git clean -fdx 之后用：只把当前磁盘状态记为升级基线，不动任何文件。磁盘与模板不一致的文件会被跳过并提示先跑 upgrade。

05 工作流：定级、阶段与门禁 任务怎么跑、谁来把门、怎么不作弊

先定级，再决定走哪条道

两问定级划出触达面闭集，命中即锁死级别，不允许"往上滑"：

  • L0 极简道：产品面 ≤ 5 个文件、未命中 L2/L3 闭集、不执行数据维护 SQL、不新增依赖。走单笔提交，消息体带一行 L0: <判据> 供机器 grep
  • L1 快速道：实现级改动，一份 plan 就是入口文档，不写 intent
  • L2 防御道：命中 4 类闭集之一——编码权威、共享契约、既有接口语义变化、全局横切口径。自检标准是"能否点名 ≥2 个行为会变的消费者"
  • L3 数据/运行时结构：schema、迁移 SQL、DI 链、鉴权与中间件管线。在 L2 之上追加独立复核，且必须在新会话中进行
红线判低会被机器硬拦——勾了"级别至少 L2/L3"的红线却定成低级别，关单直接拒绝。

FAQ

常见问题
与排障速查。

按"症状 → 原因 → 处理"的顺序整理，覆盖安装、冲突、门禁与模型四类高频问题。

一、安装与环境

安装报"unsupported language"，怎么办？

语言参数只接受两个精确值：zh-CN 与 en。zh、en-US 都会报 BAD_LANG 并返回退出码 2。

$ npx agentic-flow-kit install --lang zh-CN
Node.js 版本不够会怎样？

引擎要求 Node.js ≥ 22，这是 package.json 的 engines 声明，同时也会被 flow-kit doctor 作为一项体检检查复核。

运行 flow-kit doctor 会明确告诉你当前版本是否达标。

提示"目标目录或清单缺失"，是什么意思？

退出码 3 对应三类情况：TARGET_MISSING（--target 指向的目录不存在）、NO_MANIFEST（该目录还没装过引擎）、NO_WORKSPACE（工作区未初始化）。

多数命令需要先 install 或 adopt 产出一份清单。如果你是在别人的仓库上操作，先确认 --target 指向的是仓库根目录。

怎么知道引擎到底装了哪些东西？

看 .agents/install-manifest.json。这份清单记录了每个托管文件的哈希、已接线的宿主、栈、切面、档位以及 MCP 与权限条目，是"只动我们写过的东西"的依据。

$ flow-kit status --json

二、冲突、覆盖与升级

装的时候会不会覆盖我已经改过的文件？

默认不会。安装器把最后一次由工具写入的文本快照存在 .agents/.kit/baseline，升级时做三方合并——你的本地修改保留，引擎的新规则照常更新。

确认冲突会以非零退出码返回，加 --dry-run 可以先看完整计划再决定。

为什么提示"冲突默认跳过"？

当目标文件已经存在且内容与基线不一致时，安装器不会静默覆盖，而是跳过并在清单中记录最终文本哈希，让你自己决定怎么处理。

若你确实想强制覆盖，可以显式加 --force——但请先确认那份改动确实可以丢弃。

新 clone 的仓库要重装一遍吗？

不需要重装。用 --baseline-only 只重建基线、不动任何文件：

$ flow-kit install --baseline-only

磁盘与模板不一致的文件会被跳过，并提示你先跑 upgrade。

怎么查出门禁被谁改了？

flow-kit diff 会把每个托管文件归类：missing（缺失）、user-modified（被你改过）、kit-updated（引擎有新版）、orphan（孤儿文件）、unchanged。全程只读，零写盘。

要在 CI 里卡住未备案的改动，加 --strict，有未清理项时返回退出码 1。

清理残留文件会删掉我的东西吗？

不会。flow-kit prune 只删除哈希匹配的托管文件——也就是工具自己写下的、你没动过的那些。你改过的文件默认不删。

$ flow-kit prune --dry-run

三、工作流与门禁

L0 / L1 / L2 / L3 到底怎么分？

先过两问定级，划出触达面闭集：

  • L0 极简道：产品面 ≤ 5 文件、未命中 L2/L3 闭集、不执行数据维护 SQL、不新增依赖
  • L1 快速道：实现级改动，一份 plan 走到底
  • L2 防御道：命中编码权威、共享契约、既有接口语义变化、全局横切口径四类之一
  • L3 结构面：schema、迁移 SQL、DI 链、鉴权与中间件管线

判据重叠时取 L0。机器层面唯一防"往下滑"的硬拦是红线判低：勾了"级别至少 L2/L3"的红线却定成低级别，关单直接被拒。

为什么每次切换阶段都要我确认？

人件门是状态流转的唯一合法入口。文档只能经 confirm-doc.mjs 从 draft 走到 approved 再到 done。

交互模式下它要求你逐份确认并录入原话；委派模式记录你的原话进台账。自动跳过人件门是被明确列出的反模式。

独立复核到底复什么？

L2 / L3 强制独立复核，且必须新开干净会话、传入固定的 git range，由 review 角色模型审计。复核结论写进 verify-report.md 的 ## 结论，可被机器识别为 pass / fail / partial。

复核角色的模型必须与实现模型不同，避免"自卖自夸"。

门禁超时了怎么办？

门禁有墙钟预算，但目前是 advisory 语义：超限只警告、不阻断，阈值在 .agents/config/gate-budgets.json（全量与 scope 两档）。

预算是数据驱动的，会根据实际耗时演进。如果某个门禁长期超预算，该调的是门禁本身的范围，而不是把预算调大。

三件套缺一个会怎样？

check-spec-packages.mjs 会判不合规：spec.md 缺验收标准节、tasks.md 一个勾选项都没有、verify-report.md 缺结论或证据——都过不了。

$ flow-kit run check-spec-packages.mjs

四、宿主与模型

我的宿主支持门禁和 MCP 吗？

每个宿主的能力不同，可以直接查：

$ flow-kit list-hosts --json

例如 Codex 的门禁是用户级的 ~/.codex/hooks.json，项目内零文件；CodeArtsDoer 走 .github/hooks/；OpenCode 与 PI 不支持 hook 接线，相应规格会降级为 doctor 的 advisory 保证项。

能不能自己定义一个宿主？

可以。flow-kit new-host 按现有骨架生成适配目录与 host-meta 定义，可选带门禁、权限与 MCP 接线。

另外还支持外部宿主定义：放在 .flow-kit/hosts/*.json（项目级）或 ~/.flow-kit/hosts/*.json（用户级），也可用 --host-manifest 显式加载。优先级为项目 > 用户 > 内置。

模型怎么配？为什么复核模型不能跟实现一样？

模型按角色分配：code（实现，优先低成本高吞吐）、judgment（定级与设计，优先强推理）、review（独立复核）。

review 角色被标记为 heterogeneous，即必须与实现模型不同——否则等于让写代码的模型自己审自己。安装时可用 --model [host:]role=<id> 固定，或用 --model-mode recommend|detect|inherit 选择推荐 / 探测 / 继承宿主默认。

装完之后怎么确认它是干净的？

跑一次带证明的体检。证明链是确定性、无时间戳、不联网的文档，会重新哈希每一个受管文件：

$ flow-kit doctor --attest --out proof.json

适合把结果作为制品归档，或在 CI 里比对两次安装是否一致。

退出码怎么读？

整套 CLI 用同一套退出码：

  • 0 成功
  • 1 冲突或严格模式下的漂移
  • 2 用法错误（参数拼错、未知命令、非法枚举值）
  • 3 目标目录或清单缺失
  • 4 未知宿主
  • 5 IO 失败
  • 6 安装锁冲突（可重试）
