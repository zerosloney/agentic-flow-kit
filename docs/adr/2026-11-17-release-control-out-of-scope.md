# ADR — 发布控制面不进引擎定位（merge queue / feature flag 灰度 / 分阶段通道 / 快速回滚）
<!-- 本仓自用 ADR，按 templates/scaffold/workflow/adr/_TEMPLATE.md 形状记录；对应 BACKLOG #31（来源③）的定位决策 -->

## 背景
BACKLOG #31（2026-11-17，对 Anthropic《How the Claude Code team does code review》转述文对照）：文章把质量保障延伸到发布阶段（merge queue 合并前重检、feature flag 内部灰度、latest→stable 分阶段通道、开关快速回滚）。本仓现状定位是「AI-Native 开发工作流引擎安装器」：约束与验证发生在代码合入前——L0–L3 风险定级路由（判低机器硬拦）、pr-review 面板评审触发规则（信任边界/数据面/公共契约→面板）、CI 确定性门禁、tag-version 一致性门。不决定的代价：定位边界持续模糊，能力面无限扩张侵蚀最小面纪律。

## 决策
发布控制面**不进**引擎定位，#31 关闭、不立 ROADMAP 条目。自本 ADR 起生效；消费方 = BACKLOG 维护与后续能力扩展提案的定位判定。

## 备选与取舍
| 方案 | 关键取舍 | 风险 | 为什么没选 |
|---|---|---|---|
| 不进（关闭条目） | 引擎保持「开发工作流」边界；合入前质量门已由既有机制覆盖 | 未来装户若真需要发布仪式 hook，须重开新条目 | —（选定，owner 2026-11-17 拍板「#31 不进」） |
| 进（立 ROADMAP 最小切口：合 main 排队重检 + 回滚开关约定） | 能力面扩张但覆盖文章发布段 | 新脚本/新门/机制登记（一进一出压力）；须假设装户发布基础设施——与零依赖、不假设装户环境的安装器立场冲突；无装户需求实证 | 越出「开发工作流引擎」定位：merge queue/灰度/分阶段/回滚是组织级交付平台（PaaS/发布系统）职责，装户各自运行时异构，非安装器可分发工件 |

## 后果
- 正面：定位边界成文可引用；BACKLOG 清账（#28–#31 全闭）；同类定位问题（「文章有、引擎要不要有」）自此有先例可指认。
- 负面 / 代价：文章「质量保障延伸到生产环境」一段在引擎面无对应物——接受该缺口，理由见备选表第二行；装户侧灰度/回滚由装户自己的发布基础设施承担。
- 术语影响：无（本仓未自装 workflow 面，glossary 属装户工件）。

## 依据
- owner 裁定原话（2026-11-17）：「#31 不进」。
- BACKLOG #31 条目验收：「不进则关闭本条并记录依据；不默认开工」。
- 合入前质量门现状：`templates/engine/.agents/commands/pr-review.md` 触发规则、`new-task` L0–L3 定级路由（README 风险定级条目）、`.github/workflows/ci.yml` 确定性门禁、release.yml tag-version 一致性门。
- 推断（显式标注）：「装户发布基础设施异构、无需求实证」为基于零依赖立场与 BACKLOG 无相关装户反馈的推断，非用户调研结论。
