
**带方向的三角**

```text
              ┌──────────────────┐
              │  定义正确        │  AI 动手之前：什么是对的？
              └────────┬─────────┘
                       │ 标准
              ┌────────▼─────────┐
              │  验证正确        │  发布之前：AI 真的做对了吗？
              └────────┬─────────┘
                       │ 证据
              ┌────────▼─────────┐
              │  失败可恢复      │  上线之后：出错了怎么办？
              └────────┬─────────┘
                       │ 回流（漏掉的场景、没测过的设备、新边界）
                       └──────────► 下一次的定义
```

**三条边各一个问题、各一个动作**

| 边 | 回答的问题 | 发生时机 | 核心动作 |
| --- | --- | --- | --- |
| 定义正确 | 什么是对的？ | AI 动手之前 | 把模糊需求翻译成可验收的标准（AC） |
| 验证正确 | 它真的做对了吗？ | 发布之前 | 让 AI 拿证据（自动化）+ 人按同一份标准验收 |
| 失败可恢复 | 出错了怎么办？ | 上线之后 | 快速发现定位修复；修不了就一键回滚 |

**动手前先问自己三句**（整本手册最短的可用版本）

1. 什么是对的？
2. 我怎么证明它做对了？
3. 它错了，我接得住吗？

答不上来，就先别把需求丢给 AI。

**为什么 AI 总在返工**：同样用 AI，有人能稳定交付，有人在「生成 → 不对 → 再生成」里打转。差别不在 AI，在人。

```text
让它做个功能 ──► 很快就写完 ──► 一跑，不是你要的
     ▲                                    │
     │                                    ▼
     └──── 自己上手改 ◄── 来回几轮，开始怀疑 AI ◄── 补充说明，它改了，又改坏另一处
```

同一个模型在不同人手里，交付质量天差地别，所以问题大概率不在模型。**AI 是概率模型，模型越强只能说明出错概率越小，不是不会出错。** 既然它一定会出错，真正的问题就变成上面那三句。

## 1 什么是 AI Native Builder

**定义**

> **AI Native Builder：一个人 + AI，用 AI 原生的方式，构建从需求到交付的完整闭环。**

定义里三个部分各有分量，逐段拆。

### 1.1 一个人 + AI

主语是**一个人**。不是团队，也不是「一个人带一群人」。

这里的 AI 不是聊天框，而是一批能干活的 Agent（Claude Code、Codex、OpenCode 等）：它们能读代码库、写代码、跑测试、开浏览器验证页面、部署上线。一个人可以同时调度几个，并行处理不同任务。

人负责 AI 替代不了的部分：

- **判断什么是对的**：需求要做到什么样、哪些场景必须覆盖、什么可以不做；
- **在关键节点拍板**：验收标准对不对、设计选哪一版、能不能上线；
- **为结果负责**：出了问题，决定修复还是回滚。

所以「一个人 + AI」不是「AI 干完活，人在旁边看」，而是：**AI 负责执行，人负责判断和兜底。**

### 1.2 用 AI 原生的方式

最容易被忽略、也最关键的一段。

多数人的用法是：流程不变，在某一步用 AI 加速——原来手写代码，现在让 AI 补全；原来手写测试，现在让 AI 生成。有用，但这是「用 AI 的方式」，不是「AI 原生的方式」。

**AI 原生**的意思是：有了 AI 之后，这件事**本来就应该**这样做。不是往旧流程上贴 AI，而是假设 AI 从一开始就在，重新设计整个流程。展开见第 2 节。

### 1.3 从需求到交付的完整闭环

两个关键词：

- **从需求到交付**：起点是一个需求（可能清晰也可能模糊），终点是真正交付出去、有人在用的结果。中间的需求梳理、产品设计、UI/UX、前后端开发、测试、部署上线，这些原本分散在不同岗位的环节，现在都在一个人手里。
- **闭环**：交付不是终点。上线后的反馈、Bug、新需求要回流到下一轮。

现在很多人能用 AI 快速生成一个 MVP，设计、前后端、部署一应俱全。但**一条走完就结束的 MVP Demo 流水线不是闭环**；能从失败里学习、让下一次做得更准的，才是闭环。

## 2 AI 原生：站在需求的角度重建流程

AI 原生推翻的不是某个工具，而是「按角色分工」这个协作方式本身。

### 2.1 旧流水线的代价：交接

传统研发按角色分工，每个角色负责一段，做完交给下一个：

```text
产品经理 ──► 设计师 ──► 前端 / 后端 ──► 测试 ──► 运维
 写 PRD      出设计稿      写代码         测功能     上线
```

在没有 AI 的年代这套分工很合理——每个环节都需要大量专业技能，一个人不可能全会，所以要拆开。代价是**交接**：

- 产品经理脑子里的画面，写成 PRD 时丢了一部分；
- 设计师读 PRD 按自己理解画稿，又丢一部分；
- 开发看设计稿和 PRD 写代码，遇到没写清的地方，要么去问，要么自己猜；
- 测试拿 PRD 测，发现和开发理解的不一样，再回头对齐。

每次交接都在丢上下文、增加等待。一个需求真正花在「做」上的时间，可能不如花在「对齐」和「等」上的多。

### 2.2 在旧流水线上贴 AI

AI 来了之后最自然的做法：流水线不变，每个角色各自用 AI 提效。

```text
产品经理      设计师        前端 / 后端      测试         运维
 + AI 写 PRD   + AI 出图     + AI 写代码     + AI 写用例   + AI 写脚本
```

每个人都变快了，但交接还在。PRD 写得再快，设计师还是要读、要理解；代码生成再快，测试还是要等开发交付。**瓶颈从「做」转移到「交接」和「对齐」，而这两件事，AI 在旧结构里帮不上忙。**

这就是很多团队「人人都用 AI，整体效率却没怎么变」的原因（第 3 节有数据）。

### 2.3 案例：从电话叫车到打车软件

每个人都亲身经历过的一段历史。

十几年前在北京打车，除了路边招手，还可以打电话叫车。北京出租汽车调度中心 1995 年就成立了，专门撮合电话叫车：你打过去，话务员记下你在哪、要去哪，再去找附近空车。

电话是新技术，流程却是老流程：**乘客 → 话务员 → 调度 → 司机**，每一次转手都在丢信息、在等。2013 年北京把电话叫车统一成一个号码 96106，试运行三天，7594 个订单只成功 3707 个，成功率不到一半。报道里有个很典型的画面：电话约了车，路边几辆空车开过去，调度中心却一直等不到有车应召。

同一时期打车软件出现了：快的 2012 年在杭州上线，嘀嘀 2012 年 9 月在北京上线。不到一年，北京约有三万名司机在用，接近出租车总数的一半。

打车软件不是把电话换成手机，而是**站在「乘客要从这里去那里」这个需求上，把整条流程重做了一遍**：你的位置自动发出，附近司机直接看到，路线、价格、付款、评价都在同一个地方完成。中间那个话务员，不存在了。

|  | 电话叫车 | 打车软件 |
| --- | --- | --- |
| 新技术 | 电话 | 智能手机 + 定位 |
| 流程 | 乘客 → 话务员 → 调度 → 司机 | 乘客 ↔ 司机 |
| 本质 | 在旧流程上**贴**新技术 | 用新技术**重建**流程 |

**在旧流水线上贴 AI，就是给调度中心装一部更快的电话。话务员接得再快，那几次转手还在。**

### 2.4 案例：扣子从工作流到 Agent

打车是上一个技术周期的故事，AI 产品自己身上也在发生同样的事。

字节「扣子」2024 年 2 月上线，主打**工作流搭建**：把一件事拆成节点，某些节点里接入大模型，再把节点连成一条固定流程。本质上是在流程的某个环节里加 AI——流程是人提前画好的，AI 只负责其中几步。

这不是做错了。那会儿模型能力有限，让模型自己规划整条路径并不现实，人先把流程定死是最稳妥的做法。

但随着模型能力提升，产品形态也在变：给一个目标，它自己决策、规划整条路径、循环调用工具把事情做完，而不是走一条定死的流程。扣子自己也在往这个方向转：

- 2026 年 1 月，扣子宣布 2.0 品牌升级，推出 Agent Skills、Agent Plan 等能力。按官方说法，用户只需确定目标，扣子就能「持续执行，并向用户主动汇报、最终交付任务」；
- 2026 年 10 月 29 日，扣子发布《扣子企业版下线公告》：企业标准版和企业旗舰版 11 月 30 日起停止接受新客户购买，2027 年 12 月 31 日全面下线。

官方理由是「企业服务的产品整合与升级」，并没有说工作流过时了。但两件事放在一起看，方向很清楚：**在旧流程里加 AI，和让 AI 自己把流程走完，是两种完全不同的产品。**

### 2.5 AI 原生的研发流程

AI 原生的做法是换一个起点：**不从角色出发，从需求出发。**

问自己：有了 AI 之后，要把这个需求从一句话变成一个上线的功能，最少需要哪些步骤？每一步谁来做最合适？

以作者自己的研发工作流为例：

```text
① 需求分析与 Spec     ② 人审验收标准    ③ 设计           ④ 编码 + 自动验证
   AI 追问 + 人回答        人工闸门 ①        AI 出方案，人挑    AI 写代码、自测自修
                                                                     │
⑦ Production          ⑥ Stage 人工验收  ⑤ Stage 自动验证        ◄─┘
   监控 / 修复 / 回滚      人工闸门 ②        AI 回归测试
   AI 定位，人决定
```

两个词：**Spec** 是需求规格说明，写清目标、边界和验收标准；**Stage** 是预发布环境，和线上一致但不面向用户。

和传统流水线比的三个根本区别：

1. **没有角色之间的交接。** 需求、设计、验收标准、代码都在一个人和他的 Agent 手里，上下文从头到尾不丢。
2. **人只出现在需要判断的地方。** 人主要守两道闸门：第 ② 步审验收标准，第 ⑥ 步按验收标准验收。其余环节由 AI 执行并给出证据。
3. **质量控制点前移、后延。** 动手前先定义什么是对的，发布前用证据证明做对了，上线后能接住失败。这三个控制点就是第 4 节的三角模型。

### 2.6 AI 原生 ≠ 全自动

AI 原生不是「全交给 AI」。

AI 原生流程里人的工作量变少了，但人的每一个动作都更关键。人审验收标准时漏掉一个场景，AI 就会完美地交付一个有缺口的功能；人在 Stage 验收时走过场，Bug 就会直接到用户手里。

**所以 AI 原生对人的要求更高，而不是更低。** 你要懂需求、懂设计、懂代码、懂测试、懂上线——不是要亲手做每件事，而是要能判断 AI 在每件事上做得对不对。

## 3 为什么是现在

理由分两层：**背景**（能力已经能跑完整条流程）+ **困境**（用法还停留在按环节）。两者叠加，就是必然。

### 3.1 能力侧：从实习生到跑完全程

**几年前。** 你写一行它补下一行；问一个报错给一个答案；写好注释生成样板代码。它能做的是**某个角色**在**某个环节**里的**某个动作**，顶多算一个很能干的实习生——你得把活切得很碎，一口一口喂。

**现在。** 给 Claude Code 或 Codex 一句需求，它自己读代码库、拆任务、写代码、跑测试、看报错、修复、再测试，必要时开浏览器检查页面，最后把改动部署到预发布环境。这条路径上原本站着产品、开发、测试、运维好几个角色，现在它一个人从头走到尾。

不只是体感。专门评估 AI 能力的研究机构 METR 用一把直观的尺子量：**AI 能独立完成的任务，相当于人类专家要干多久的活**。他们发现这个时长过去几年大约**每 7 个月翻一倍**；最近两年还在加速，大约**3 个月翻一倍**。

几年前，AI 能独立搞定的是「改一个函数」这种几分钟的活；现在，它已经有能力完整做出一个产品从 0 到 1 的 MVP，持续运转几个小时甚至几天。

**每个人都在变得更「全栈」。** Anthropic 研究自己员工的工作方式，得出一句话：

> Claude 让每个人的工作都变得更「全栈」。

写后端的人也能自己做出像样的前端界面——不是突然学会另一门手艺，而是 AI 把「另一个角色的执行」接了过去，人只需要判断做得对不对。

同一研究里还有一个细节值得记住：大多数人觉得，能**完全放手**交给 AI 的工作，只占自己工作的一小部分。**AI 能跑完流程，但对结果负责的仍然是人。**

| 过去 | 现在 |
| --- | --- |
| AI 做一个角色里的一个动作 | AI 跑完一条涉及多个角色的流程 |
| 人把活切碎了喂给 AI | 人给出需求和标准，AI 自己拆、自己做、自己验 |
| AI 是工具 | AI 是队友，一个人可以同时带好几个 |

**能力已经到位了。** 可是能力到位，不代表大家都用对了。

### 3.2 用法侧：单点提效不等于整体提效

推演一个很常见的团队：两个产品经理、一个设计师、四个开发、两个测试，公司给每个人都开了 AI 工具，大家都用得很积极。

| 时间 | 发生了什么 |
| --- | --- |
| 周一 | 开发发现以前一天写完的功能现在半天写完，个人代码产出差不多翻倍 |
| 周二 | 代码要合主干，得有人评审。评审的还是那几个资深开发，他们自己也在写代码。待评审列表从五个涨到十个 |
| 周三 | 测试收到的待测功能翻倍，可一天能走完的用例没多多少。有些功能在评审里等了两天还没轮到测试 |
| 周四 | 产品经理发现好几个功能做出来和自己想的不一样。不是 AI 写错了，是需求文档本来就没写清楚。以前开发会来问一句，现在 AI 不问，直接按自己的理解写完。返工 |
| 周五 | 复盘会上大家都说 AI 让自己快了不少。可这周真正上线的功能，和上个月差不多 |

问题在哪？**写代码这一段确实变快了，但交付是一条流水线，流水线的速度取决于它最慢的那一段。** 写代码快了，堵点就移到评审、测试和需求对齐上，而这几段 AI 在旧的分工结构里帮不上忙。

**这不只是推演。**

- 研发效能公司 Faros AI 分析了一万多名开发者的数据，看到的几乎就是上面这一周：AI 用得多的团队，合并的代码多了 98%，但代码评审的时间也多了 91%；放到整个公司层面，**看不出 AI 带来了显著的效率提升**。
- 谷歌 DORA 团队调查约五千名技术从业者，结论只有一句话：

  > AI 不会修好一个团队，它只会放大团队里已经存在的东西。

  流程顺的团队，AI 让它更顺；流程堵的团队，AI 让它堵得更快。

**赢家做对了什么。** 波士顿咨询的调查发现，从 AI 里拿到真实价值的企业有一个共同点：**它们不是在每个环节各自用 AI，而是把工作流端到端地重新设计了一遍。**

回到那个团队：如果不是十个人各自加速自己那一段，而是让每个需求都由一个人加 AI 从头负责到尾——需求自己问清楚，验收标准自己写好，代码让 AI 写、让 AI 先验，最后自己验收上线——周二那条评审队列、周三那堆待测功能、周四那次返工，都不会以同样的方式出现。

不是给调度中心换一部更快的电话，而是把打车这件事重做一遍。

### 3.3 程序员的困境：两端同时收紧

企业卡在「按环节用 AI」，程序员个人也卡在同一个地方：**按角色定位自己**。如果你只守着「写代码」这一段，AI 每进步一点，你守着的那一段就窄一点。

**应届生：在执行层面，卷不过 AI。** 以前一个计算机专业毕业生是这样成长的：先写简单页面、修小 Bug、补测试用例，在一个个小任务里学会判断。可这些「练手的活」恰恰是今天 AI 做得又快又好的部分。

- 2025 年 4 月，Shopify 的 CEO 在内部信里要求：在申请更多人手之前，团队必须先证明这件事为什么不能用 AI 完成。
- 同年 2 月，Salesforce 的 CEO 在财报会上说，工程团队效率提升了 30%，「今年我们不会再招新的工程师」。
- 纽约联储的数字：美国 22–27 岁的近期本科毕业生里，计算机工程专业失业率约 7.8%，计算机科学约 7.0%，在 74 个专业里分别排第 2 和第 4 高。值得注意的是，找到工作的人薪资依然不错——**难的不是待遇，是门槛。**
- 普华永道说得更准：

  > AI 正在拿走一部分曾经充当「学徒期」的日常工作，同时让人在职业生涯更早的阶段，就需要判断力、领导力和适应力。

**资深程序员：有点像「老中医」。** 另一头情况正好相反。

- Indeed 统计美国招聘广告：2026 年第一季度，软件开发岗位里**资深岗位（5 年以上）占 69.3%，入门级只占 4.5%**，是所有行业里入门级占比最低的。作为对比，全美所有行业招聘里资深岗位只占约 14%。
- 斯坦福一项研究给出更细的画面：从 2022 年底到 2026 年 6 月，22–25 岁年轻人的就业还低于起点，**而每一个更年长的年龄段都在增长，35–40 岁增长了 11%**。研究还发现，越是依赖「默会知识」（说不清、写不下来、只能靠经验积累）的工作，有经验的人就业增长得越快。

数据说明的是**经验**的价值，不是年龄本身。企业不在乎你几岁，在乎的是：

- 你见过多少种问题，能一眼看出 AI 给的方案哪里不对；
- 你能覆盖多少个角色，需求、设计、代码、测试、上线都能判断；
- 你能不能做架构层面的取舍，知道哪些地方值得 AI 多花力气，哪些地方一步走错就很难回头。

这三样恰好就是 AI 做不了、而 AI Native Builder 必须做的事。

**新人的路在哪里。** 不是说新人没有出路——连亚马逊云的 CEO 都公开反对「用 AI 替掉所有初级员工」：如果今天不招新人，十年后谁来成为资深？但新人的成长方式确实变了：**不再是靠写够一万行代码熬成资深，而是要尽早学会判断。** 什么是对的、怎么证明它对、错了怎么办。

**困境的根源是同一个：**

> AI 的能力已经能覆盖一整条流程，但人和组织还在按角色、按环节使用它。

### 3.4 交汇：什么在变稀缺

|  | 背景（3.1） | 困境（3.2 / 3.3） |
| --- | --- | --- |
| 发生了什么 | AI 能独立完成的任务越来越长，从做一个动作到跑一条流程 | 企业人人在用 AI，整体交付却没快多少；入门岗位在收缩 |
| 本质 | **能力的供给**已经覆盖了完整闭环 | **使用的方式**还停留在按角色、按环节 |
| 缺口 | — | 能把 AI 的能力组织成一个完整闭环、并对结果负责的人 |

能力到了，用法没跟上，中间的缺口就是一个新角色：**一个人 + AI，用 AI 原生的方式，构建从需求到交付的完整闭环。**

所以这不是个人偏好，而是**必然的趋势**：

- 对企业来说，这是打破「单点提效、整体不提效」的方式——领先企业的共同做法就是端到端重塑工作流；
- 对程序员来说，这是走出「守着一段越来越窄的环节」的方式——招聘市场奖励的正是对结果负责、跨环节判断的能力。

**什么在变贵？** 执行越来越便宜，稀缺的是三种判断（AI 能帮你做很多，但不能替你负责）：

1. 知道什么是对的：把模糊需求翻译成可验收的标准；
2. 能证明它做对了：设计验证方式，让 AI 拿出证据，自己再做最后判断；
3. 出了错接得住：提前准备好发现、定位、修复和回滚的手段。

这三件事，恰好就是三角模型的三条边。

### 3.5 三条冷静的限定

- **团队不会消失。** 一个人 + AI 能覆盖完整闭环，不代表所有工作都该一个人做。更可能的形态是：团队由一个个能独立闭环的 Builder 组成，协作的单位从「岗位」变成「需求」。
- **会用 AI 工具不够。** 工具已经普及，效果却在分化。分化的原因不是工具，而是有没有一套保证交付质量的方法。
- **承认数据的局限。** 有些样本有偏差，有些只是相关性，有些结论还在快速变化。所以数据只用来说明方向，不用来「证明」趋势。方向是清楚的：**AI 能力在往完整闭环走，市场在奖励能驾驭完整闭环的人。**

带走一句话：**执行越来越便宜，稀缺的是三种判断：定义正确、验证正确、失败可恢复。**

## 4 核心方法：交付质量三角模型

> 怎么成为 AI Native Builder？答案是：**为你的每一个需求，构建一个能保证交付质量的模型。**

### 4.1 比速度更重要的，是交付质量

作为 AI Native Builder，不太需要讨论「用 AI 写代码有多快、一天能做多少个功能」。速度不稀奇，AI 一口气可以生成成百上千甚至上万行代码。

真正的问题是：**它交付出来的东西，质量过不过关？**

AI 是概率模型，没人能保证它百分之百做对。所以目标不是让 AI 永不出错，而是让整个交付过程可控：**尽量做对、证明做对、出错能接住。** 这三件事就是三角模型的三条边。

### 4.2 第一条边：定义正确

**问题：什么是对的？发生在 AI 动手之前。**

如果你自己都不知道这个需求做到什么程度算对，AI 来做肯定不可能对——它只会做得更乱：能力再强，没有一个好的指挥者，也只会胡乱打仗。

定义正确，本质上就是**定义验收标准**。放到产品研发里有两个面：

- **功能行为正确**：用户的真实路径要被端到端走通，验收方式是 E2E（端到端）测试用例。这是最重要的一面。
- **UI/UX 正确**：页面结构、交互流程、视觉风格、组件一致性，验收方式是交互原型、设计稿、设计系统（DESIGN.md）。

**常被忽略的动作：人逐条 Review 验收标准。** AI 生成的验收标准往往看起来很完整，但会漏掉关键路径。

举个谁都用过的功能：**上传头像**。让 AI 写验收标准，它通常写这几条：

- 选一张图片，上传成功，头像更新；
- 选了不是图片的文件，提示格式不对；
- 没登录时不能上传。

看起来挺全。但拿起手机想想自己平时怎么用：

- 手机拍的原图动不动十几 MB，图太大怎么办？
- 地铁里上传到一半网断了，是失败、重试，还是卡住不动？

这两条恰恰是真实用户最常遇到的。AI 没写，不是因为它笨，而是因为它不在你的场景里。**把这些场景补进验收标准，是人的工作。**

**怎么才能定义正确？** 最快的一条捷径是：**找到一个符合你期待的样本。** 有了样本，「对」就有了参照物。

### 4.3 第二条边：验证正确

**问题：AI 真的做对了吗？发生在发布之前。**

正确定义好了，交给 AI 执行。它可能做了很多事，最后告诉你「完成了」。但你需要验证：它做的事是否真的符合事先定义好的那个「正确」。

两种方式，缺一不可：

- **自动化验证**：代码规范检查、单元测试、集成测试，以及最关键的 E2E 测试。比如让 AI 用 Chrome DevTools 真正打开页面，按验收标准一条条走一遍；不通过就自己修，修完再验。
- **人工验证**：在预发布（Stage）环境，人按照同一份验收标准，一条一条地确认。机器给证据，人做产品判断。

注意：验证的依据是**第一条边定义的标准**，不是「看起来不错」。没有定义，就没有验证。这就是三条边有先后顺序的原因。

### 4.4 第三条边：失败可恢复

**问题：出错了怎么办？发生在上线之后。**

就算定义正确、验证也通过了，发布之后仍然可能出问题：线上出 Bug、用户在你没测过的设备上看到不一样的效果、收到负面反馈。

需要一套危机处理机制，两层：

1. **能快速修复**：能快速知道是什么原因导致的失败。这要靠日志、监控、告警、错误上报——有了这些信息，AI 才能帮你快速定位和修复。
2. **修不了就回滚**：如果不能快速修复，就能一键回到上一个稳定版本，先止损，就像撤回一条消息。

### 4.5 缺一条会怎样

| 缺了哪条边 | 会发生什么 |
| --- | --- |
| 定义正确 | AI 在很努力地完成一个错误的需求。白白浪费 token 和你的注意力，后续还要花很长时间收拾残局 |
| 验证正确 | AI「骗」了你，你也不知道。它说完成了，到了生产环境，给你报一个 P0 级别的 Bug |
| 失败可恢复 | 线上报错，既修不快，也回滚不了。一个小问题被放大成事故 |

没有 AI 的时候，人写的代码我们都不能完全信任，更何况是 AI 写的。

### 4.6 为什么是「三角」，又为什么有箭头

有人问：这三条边明显有先后顺序，先定义、再验证、再恢复，为什么叫三角，不叫流程？

两个意思都在：

- **三角说的是缺一不可。** 三角形少一条边就立不住，交付质量也一样。
- **箭头说的是顺序和循环。** 定义正确在 AI 动手之前，验证正确在发布之前，失败可恢复在上线之后。而失败中学到的东西（漏掉的场景、没想到的设备、新的边界条件）会回流到下一次的定义里，让下一轮定义得更准。

所以准确地说，它是一个**带方向的三角**：每转一圈，交付质量就更稳一点。

### 4.7 同一个三角，不同的强度

不是每个需求都要走一遍最重的流程。想想做饭：办一桌年夜饭、给自己煮一碗面、发现汤咸了要补救，三件事用心程度完全不同，可每一件都绕不开同样的三个问题：做成什么样算好？怎么知道做好了？砸了怎么办？

|  | 办一桌年夜饭 | 煮一碗面 | 汤咸了 |
| --- | --- | --- | --- |
| 定义正确 | 提前定菜单，问清谁忌口、几个人吃 | 心里想好：加不加蛋，要不要辣 | 先尝一口，确认是咸，不是淡了 |
| 验证正确 | 每道菜出锅前试味，对着菜单清点 | 出锅尝一口 | 加水之后再尝，和刚才对比 |
| 失败可恢复 | 备一两道快手菜，实在不行叫外卖 | 煮坏了再煮一碗 | 越改越糟，就重新做 |

放到软件研发里，拿一个记账 App 举例：

|  | 从零做这个 App | 加一个「导出 Excel」按钮 | 修一个 Bug：「月底统计少算了一笔」 |
| --- | --- | --- | --- |
| 定义正确 | 完整需求文档：用户旅程、每个功能的验收标准、设计稿；人逐条审 | 一张卡片写清楚：导出哪些字段、空数据怎么办、不改什么 | 先写清楚：怎么复现、现在是什么、应该是什么；找到真正的原因 |
| 验证正确 | 全套自动化测试 + 在预发布环境按验收标准逐条走一遍 | 为每条标准写测试，自己点一遍导出的文件 | 用同一个复现步骤再走一遍，确认那一笔算上了 |
| 失败可恢复 | 上线后看日志、错误报警；出大问题回滚到上一版 | 同左 | 同左；修了反而更糟，立刻回滚 |

**差别只在用心的程度，不在质量要求。三条边一条都不能少。**

### 4.8 不只是程序员的模型

本手册是程序员版，但三角模型的底层逻辑适用于任何领域。比如用 AI 写一份材料：

- **定义正确**：找一份你认可的范文，写清楚这份材料给谁看、要让他做出什么决定、必须包含哪些内容；
- **验证正确**：让 AI 对照这些标准逐条自查，再由你或一位读者按同样的标准读一遍；
- **失败可恢复**：发出去之后，读者有疑问能快速补充说明；写错了能马上发更正版本。

说法换了，逻辑不变。

### 4.9 怎么成为 AI Native Builder

> **拿到任何一个需求时，都能为它构建出一个 AI Native 交付质量三角模型，并用它完成从需求到交付的闭环。**

## 5 把三角装进研发流程

第 4 节讲的是模型，这一节讲模型怎么落到一条真实的流水线上。

### 5.1 流程骨架与两道人工闸门

```text
① 定义正确 ──► 人工闸门 A ──► ② 实现 ──► ③ 验证正确 ──► 人工闸门 B ──► ④ 上线 + 失败可恢复
  AC / Spec      审标准          AI 编码      自动验证 + 看图      按 AC 验收        可回滚 · 回流新 AC
```

对应第 2.5 节的七步流程：Spec 与追问、审验收标准（闸门 A）、设计、编码与自测自修、Stage 自动验证、Stage 人工验收（闸门 B）、Production 监控与回滚。

| 阶段 | AI 做什么 | 人做什么 |
| --- | --- | --- |
| 定义正确 | 追问需求、起草 Spec 与验收标准、找参照样本 | 逐条审：漏了哪些真实场景、哪些可以不做 |
| 实现 | 读代码库、拆任务、写代码、写测试、自测自修 | 只在方案取舍上拍板 |
| 验证正确 | 跑 lint / 单测 / 集成 / E2E，逐张看截图修问题 | 在 Stage 按同一份标准验收 |
| 上线与恢复 | 部署、看日志与告警、定位问题、执行回滚 | 决定是否发布、修复还是回滚 |

### 5.2 每个环节都问同样三个问题

从一个官网放大到完整产品，环节会变成：梳理用户旅程产出 Spec；信息结构、高保真设计、设计系统；前端、后端、数据库、移动端；单元 / 集成 / E2E 测试与预发布环境；部署、监控、告警、回滚；上线后大功能、小功能、Bug 修复并行流转。

每一个环节都要回答同样的三个问题：**什么是对的？怎么证明它做对了？出了错怎么办？**

### 5.3 环节之间必须咬合（整理）

三角不是每个环节各转一次就完事，环节之间还要互相喂：

| 咬合点 | 具体要求 |
| --- | --- |
| 设计 → 测试 | 设计的验收标准要能直接流进 E2E 用例，不是两套说法 |
| 分支 → 回滚 | 分支策略要支撑回滚（能定位到上一个稳定版本、能单独下线一个改动） |
| 架构 → 可改 | 项目架构要让 AI 读得懂、改得动：边界清晰、约定成文、测试可跑 |
| 事故 → 标准 | 每一个线上问题都要回流成一条新的验收标准，否则下一圈还会踩 |

如果让你自己从 0 到 1 搭这样一套交付模型，第 7 节的弯路会在每一个环节上重演一遍，而且更多。

## 6 实操：有现成交付模型时

> 场景：你要做的东西，已经有人把交付模型总结好了。

### 6.1 交付模型长什么样

**从现阶段看，交付模型对外的表现就是一个 Skill**：一份交给 Coding Agent 的说明书，加上模板和脚本，规定了 AI 应该按什么路径调度、做到什么程度算对、怎么验证、出错了怎么办。

换句话说：**Skill 就是一条写下来的 AI 调度路径。**

书里配套的这类模型叫 `product-demo-site`（产品演示官网交付模型），安装与用法见 [12.2](#122-product-demo-site产品演示官网交付模型)，原文见 <https://iamlv.cn/book/appendix/skill>。

### 6.2 三角几乎是现成的

**定义正确：只需要一句话。** 定义正确最快的捷径是找到一个符合期待的样本；一个现成的交付模型就是一个已经拆解好的样本——怎么讲、讲几幕、首屏放什么、字幕写几行、怎么验证，全在里面。所以你只需要给两样东西：

1. 这个交付模型（product-demo-site）；
2. 你的产品资料：一个产品链接，或者产品的代码库。

然后说一句：「用 product-demo-site 给我的产品做一个演示官网」。

剩下的「定义」工作 Agent 自己去做：打开产品截真实界面、读出产品自己的配色和字体、读一遍首页和文档、起草方案（一句话承诺、演示哪几个场景、每一幕对应哪个界面、怎样算做好了）。你要做的只是**审一遍这份方案**。

**验证正确：一条命令，加上看图。**

- 机器：一条 `pnpm verify`，在电脑和手机两种宽度下逐幕截图，自动检查字幕、溢出、报错、读屏、减少动态效果；
- Agent 自己看图：逐张看截图，找机器发现不了的问题；
- 人：最后在真实设备上按标准走一遍。

**失败可恢复：可回滚，加回流。** 部署到能一键回滚的地方，上线后在几种常见浏览器里抽检。出了问题，修好之后把它变成下一次的检查项。

### 6.3 实录：一个官网从一句话到上线

全过程只有一轮（产物是这本小册的官网）：

1. **一句话开始**：「用 product-demo-site 给这本小册做一个演示官网，小册在本地这个地址。」
2. **Agent 自己研究**：打开小册，截下 6 个真实页面（首页、第 1、5、6、7、8 章），浅色深色各一套；读出小册自己的配色——米白纸张底色、墨色正文、朱红色主色、衬线标题。
3. **起草方案，人审一遍**：按小册自己的顺序，镜头依次走过这 6 页（是什么、为什么、怎么成为，再到两个案例），每页推近到最关键的一段，配一句标注，最后拉远看到主线。
4. **生成和验证**：自动检查全部通过；Agent 看截图时顺手修掉几处小问题，比如手机上推近后字太小。
5. **人工验收，完成。**

从一句话到上线，用了一次对话的时间。

### 6.4 有交付模型 vs 没有交付模型

|  | 有交付模型（本节） | 没有交付模型（第 7 节） |
| --- | --- | --- |
| 什么是对的 | 一句话 + 产品链接，Agent 起草，人审一遍 | 并行试了三个方向，转了好几圈才说清楚 |
| 怎么证明对 | 一条命令 + 看图 + 人工验收 | 目测、手写测试，靠人兜底 |
| 出错了怎么办 | 回滚流程和抽检清单已经写好 | 在别人的设备上踩坑后再补 |
| 耗时 | 一次对话 | 约 6 周、45 个提交 |

用现成交付模型的人用得很轻松。但你不能指望每个需求都有一个现成的交付模型——如果没有呢？回到这个交付模型诞生之前。

## 7 实操：没有交付模型时，从 0 到 1

> 场景：没有样本、没有模型，三角是怎么一圈一圈转出来的。

### 7.1 起点：一个三条边都是虚线的三角

一开始对官网的全部想法就是一句话：「给 CanvasAgents 做一个好看的官网。」

| 边 | 一开始的样子 | 问题在哪 |
| --- | --- | --- |
| 定义正确 | 「做几版好看的官网」 | 什么叫好看？给谁看？看完要做什么？全都没说 |
| 验证正确 | 我打开看一眼，凭感觉 | 感觉每天都不一样，也说不出哪里不对 |
| 失败可恢复 | 交付给我，行就上线；不行让 AI 再生成一版 | 每一版都从头来，上一版的教训没有留下来 |

这就是「一句话丢给 AI，生成、不满意、再生成」的用法。不同的是，这一次知道自己在转一个三角，于是每转一圈都刻意问自己：**这一圈学到了什么，能不能写进下一圈的定义？**

6 周、45 个提交，压缩成一句话：**同一个三角模型，转了 5 圈。**

### 7.2 五圈

**第 1 圈 · 模糊目标**

- **定义**：做几版好看的官网。让 AI 并行做了三版——杂志风（深色长文排版）、明亮产品说明书风（浅色干净）、滚动叙事（往下滚，用网页模拟产品被使用的过程）。
- **判断**：三版都「还不错」，但没有一版「就是它」。前两版在用文字和图片**介绍**产品；只有第三版在**演示**产品——访客能看到画布、终端、Agent 怎么配合。
- **回流**：官网要演示产品怎么工作，而不是摆几张好看的图。前两版停在这一圈，第三版这条路继续往下走。

**第 2 圈 · 演示要真**

- **定义**：滚动叙事，演示产品怎么工作。
- **判断**：滚动叙事有了，但太假——完全没有展示真实的产品界面，产品使用方式都是造出来的。
- **回流**：一切都要真，用产品的真实界面。

**第 3 圈 · 多端炫技**

- **定义**：在「真」的基础上还想要「电脑、手机都能用」，做了一段设备变形动画：笔记本合上变手机，手机再像书一样展开成折叠屏。
- **判断**：效果确实炫酷，这版还上线运行了一段时间。但收到用户反馈：看起来挺炫，可这个功能比较通用，同类产品都有类似功能。
- **回流**：官网不能只放炫酷动画演示「功能长什么样」，而要聚焦这个产品能解决什么问题、主要价值在哪——**用滚动叙事的方式，演示产品实际能解决的问题、实际的价值，以及它在什么场景下发挥作用。**

  这一圈最贵。整个官网的定义被炫酷效果带偏了，一直到用户反馈才知道这种效果不该放在首页。

**第 4 圈 · 收窄范围，只讲一个故事**

- **定义**：整页推倒重来，**只讲一个故事、一个真实的需求**：演示一个门店在线预约的需求，在一张画布上从需求梳理到发布上线，一共七幕。
- **判断**：结合反馈，大家能很直观地知道这个产品能解决什么场景下的什么问题。「讲故事」的演示版本方向对。
- **回流**：把这个经验沉淀下来，形成一个可以稳定交付的三角模型——本质上就是一个 Skill。

**第 5 圈 · 沉淀成交付模型**

最后一圈不是在做官网，而是把前四圈学到的东西打包成别人也能直接用的交付模型：

| 边 | 现在的样子 |
| --- | --- |
| 定义正确 | 给一个产品链接或代码库，它自己研究产品、截取真实界面、起草方案；人只需要审一遍 |
| 验证正确 | 一条命令，在电脑和手机宽度下逐幕截图并自动检查，再加一份「看图清单」和一次人工验收 |
| 失败可恢复 | 可回滚地上线，上线后在几种常见浏览器里抽检；每一个线上问题都变成下一次的验收标准 |

**关于 Skill 怎么写**：它就是在三角模型不断迭代的过程中，基于最后稳定下来的那个三角模型，自然而然产出的结果——不是先写 Skill 再套流程。

### 7.3 起点和终点并排看

| 边 | 第 1 圈 | 第 5 圈 |
| --- | --- | --- |
| 定义正确 | 「做几版好看的」 | 产品资料 + 一个经过四圈验证的交付模型 |
| 验证正确 | 我看一眼 | 自动截图 + 看图清单 + 人工验收 |
| 失败可恢复 | 不行就再生成一版 | 可回滚上线 + 抽检 + 问题回流成新标准 |

**每一圈的失败可恢复，都不只是把这一次的问题修好，而是把失败变成下一圈的定义：**

```text
第 1 圈「都不对」          ──► 第 2 圈的「演示产品怎么工作」
第 2 圈「演示是造出来的」  ──► 「一切都要真」
第 3 圈「炫技跑偏」        ──► 第 4 圈的「收窄范围，只讲一个故事」
第 4 圈「讲一个故事」有效  ──► 第 5 圈的交付模型
```

## 8 动手：为你的需求搭一个三角

> 从读到做：一句模板 + 两条路的选择。

### 8.1 通用提示词模板

把 `{ }` 换成你自己需求相关的内容，直接交给 Agent：

```text
用 ai-native-builder-tutor，帮我为下面这个需求搭一个「AI Native 交付质量三角模型」。

我的需求：{一句话描述你的需求，比如：给我们的记账 App 加一个「导出 Excel」功能}
项目背景：{项目类型、技术栈、现在的测试和部署方式}
我的期待：{做到什么程度算好；有没有可以参照的样本}

请你：
1. 先基于小册里的方法，判断这个需求适合多重的三角，以及最快搭起来的路径；
2. 有不清楚的地方先问我，一次只问一个问题；
3. 需要小册之外的知识（框架、工具、最佳实践）时，去查资料补上，并告诉我来源；
4. 最后给我这个需求的三角模型：验收标准（定义正确）、自动化加人工的验证方式（验证正确）、上线后的发现、修复和回滚方案（失败可恢复）。
```

> **提醒**：AI 生成的三角模型建议仅供参考。最后拍板的还是你自己——验收标准对不对、验证够不够、回滚方案能不能用，都要你逐条过一遍。

要让模板生效，需要配套的答疑 Skill `ai-native-builder-tutor`（见 [12.1](#121-ai-native-builder-tutor答疑与带读)）。

### 8.2 两条路怎么选

|  | 第一条路：自己摸索，让 AI 辅助 | 第二条路：先看一套成熟的交付模型 |
| --- | --- | --- |
| 做法 | 拿着这套方法，从手上下一个需求开始，一圈一圈地把自己的三角转出来 | 先看成熟交付模型在完整产品研发里怎么用，再按自己的项目调整 |
| 代价 | 会把别人踩过的坑再踩一遍，然后长出属于你自己的模型 | 需要投入去学一套别人的体系，未必完全贴合你的场景 |
| 适合 | 愿意花时间、享受摸索过程 | 希望少踩坑、尽快在完整产品研发里跑通 |

作者本人的捷径是把成熟交付模型用在完整产品研发中的过程整理成了一门课（<https://canvasagents.dev/course>）。

无论选哪一条，有一件事一样：**下一个需求来的时候，先别急着丢给 AI。** 先问那三个问题。

## 9 检查清单

> 以下清单为按三角模型**整理**的操作化条目，用于每次交付前逐条核对；原文只给模型与案例，未逐条列出。

### 9.1 需求进 AI 之前：定义正确

- [ ] 能用一句话说清「做成什么样算对」，而不是「做个好看的 / 好用的」
- [ ] 写清了给谁用、用完要完成什么动作
- [ ] 功能路径有 E2E 级别的验收标准（不是「能点」而是「按真实路径走通」）
- [ ] UI/UX 有可对照的依据：原型 / 设计稿 / DESIGN.md
- [ ] **至少补了三条 AI 大概率会漏的真实场景**（大文件、弱网、中断重试、空数据、多端差异）
- [ ] 写清了「不做什么」——边界之外不实现
- [ ] 有一个符合期待的参照样本（有则定义成本骤降）
- [ ] 验收标准是人逐条 Review 过的，不是 AI 一次生成就采用

### 9.2 发布之前：验证正确

- [ ] 验证依据是 9.1 那份标准，不是「看起来不错」
- [ ] 自动化覆盖：lint / 单测 / 集成 / E2E
- [ ] E2E 真按用户路径跑过（浏览器真实打开，而不是 mock）
- [ ] 失败时 AI 先自修再复验，而不是把失败清单丢给人
- [ ] 视觉类产物由 Agent 逐张看图，而非只看退出码
- [ ] 在 Stage 环境按同一份标准人工走了一遍
- [ ] 机器证据与人的判断都留档（截图、日志、结论）

### 9.3 上线之后：失败可恢复

- [ ] 日志、监控、告警、错误上报可用，能定位「哪一步失败」
- [ ] 有明确的一键回滚路径，且**验证过**能回滚
- [ ] 分支/部署策略支持单独回退某个改动
- [ ] 上线后有抽检清单（几种常见浏览器 / 设备 / 网络）
- [ ] 出了问题有明确的决策人：修还是回滚
- [ ] 每个线上问题都回流成一条新的验收标准

### 9.4 反模式清单（整理）

| 反模式 | 症状 | 对应哪条边坏了 |
| --- | --- | --- |
| 一句话丢给 AI | 生成 → 不对 → 再生成，每轮从头来 | 定义正确 |
| 用「好看/好用」当标准 | 每轮评价都不一样，说不清哪里不对 | 定义正确 |
| 把 AI 的验收标准直接采用 | 清单很完整，漏的恰好是最常见场景 | 定义正确 |
| 只信「它说完成了」 | 上线后才发现 P0 | 验证正确 |
| 只看测试通过率，不看产物 | 断言对，界面错 | 验证正确 |
| 在旧流水线上贴 AI | 个人变快、整体不变，堵点移到评审与测试 | 不是边的问题，是流程没重做（第 2 节） |
| 没验证过回滚 | 出事时发现回滚脚本本身是坏的 | 失败可恢复 |
| 修完就完事 | 同一个问题下次换台设备再犯 | 失败可恢复（回流） |
| 先写 Skill 再套流程 | Skill 写得很漂亮，但没经过任何一轮真实失败 | 全部（模型未验证） |

## 10 术语表

| 术语 | 含义 |
| --- | --- |
| **AI Native Builder** | 一个人 + AI，用 AI 原生的方式，构建从需求到交付的完整闭环 |
| **AI 原生（AI Native）** | 假设 AI 从一开始就在，站在需求的角度重新设计流程；区别于在旧流程上「贴」AI |
| **完整闭环** | 从需求到交付，并且上线后的反馈、失败能回流到下一轮 |
| **AI Native 交付质量三角模型** | 定义正确、验证正确、失败可恢复，三条边缺一不可，按顺序循环 |
| **定义正确** | 在 AI 动手之前定义「什么是对的」，本质是验收标准；软件研发中主要是 E2E 用例和 UI/UX 标准 |
| **验证正确** | 在发布之前证明 AI 真的做对了：自动化验证提供证据，人工验收做最终判断 |
| **失败可恢复** | 上线之后能快速发现、定位、修复；修不了就回滚 |
| **验收标准（AC）** | Acceptance Criteria，判断一个需求是否完成的可检验条件 |
| **Spec** | 需求规格说明，包含目标、边界、验收标准 |
| **E2E 测试** | 端到端测试，按用户的真实路径走通整个功能 |
| **Stage** | 预发布环境，和线上一致但不面向用户 |
| **交付模型** | 为一个需求构建好的三角模型的具体形态；现阶段表现为一个 Skill（说明书 + 模板 + 脚本） |
| **Skill** | 交给 Coding Agent 的说明书加模板和脚本，规定调度路径、完成标准、验证方式与失败处理；本质上是一条写下来的 AI 调度路径 |
| **回流** | 把这一轮的失败与反馈变成下一轮的验收标准 |
| **默会知识** | 说不清、写不下来、只能靠经验积累的知识 |

### 12.1 `ai-native-builder-tutor`：答疑与带读

### 12.2 `product-demo-site`：产品演示官网交付模型

- **能力**：首屏一句承诺 + 产品真实截图；往下滚，镜头在真实界面之间移动、推近、标注，分几幕演示产品如何解决访客认得出的痛点；最后拉远看全貌，收束到一个按钮。配色和字体来自你的产品，不是某个参考网站。
- **结构**：`SKILL.md`（工作流、硬规则、何时不用）+ `references/`（brief 模板、分镜模型、视觉规则、验证、上线与恢复）+ `template/`（React + Vite + Tailwind v4 + motion）+ `scripts/capture.mjs`（真实截图 + 品牌配色 + 元素位置）+ `e2e/verify.mjs`（逐幕截图 + 断言）。
- **用法**：「用 product-demo-site 给我的产品做一个演示官网」，或「……给这个项目做一个演示官网，代码在 ~/code/my-app」。Agent 会自己研究产品、起草 `BRIEF.md` 给你审，**在你确认之前不会写分镜代码**。
- **环境**：Node.js 20+、pnpm；`pnpm verify` 需要本机 Chrome，没有则用 Playwright 自带 Chromium（先 `npx playwright install chromium`）。

下载：<https://iamlv.cn/downloads/product-demo-site.zip>；原文：附录 A · <https://iamlv.cn/book/appendix/skill>
