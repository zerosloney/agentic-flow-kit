# codebase-design — 接口形状怎么判

## 触发

- Design 章要在 2 个以上接口 / 分层方案里选一个。
- 复核时怀疑「这层是直通层 / 这个抽象没藏住任何东西」。
- 拆任务前要先划接缝，否则并行派发会互相踩。

## 核心

**复杂度 = 依赖 + 模糊。** 深模块用一个小接口藏住大量实现知识；浅模块接口宽、藏得少，只是把复杂度搬给调用方。判形状不靠审美，靠下面四条可判定的问句。

## 词汇（比选时统一用词）

| 词 | 含义 |
|---|---|
| deep module 深模块 | 接口小、实现能力大；调用方不需要知道内部事实 |
| shallow module 浅模块 | 接口相对实现过大；典型是直通层与薄包装 |
| information hiding 信息隐藏 | 内部决策（格式、顺序、存储、重试）不外泄到调用方 |
| seam 接缝 | 可替换实现的边界：测试替身、并行实现、跨宿主适配都挂在它上面 |
| deletion test 删除测试 | 把它删掉，复杂度是集中到一处还是扩散到 N 个调用点 |
| leverage 杠杆 | 一处改动能让多处受益的位置 |
| pass-through 直通 | 只做转发 / 改名 / 加一层 try-catch 的函数或类 |
| temporal decomposition 时序分解 | 按「先读后写再校验」的执行顺序切模块，而不是按知识切——同一事实散在多处 |

## 四条判据（每条给结论 + 证据）

1. **删除测试**：删掉它，复杂度集中还是扩散？扩散 → 它在藏东西（深，保留）；集中 → 直通层（浅，考虑合并进调用方或被调方）。
2. **接口面**：调用方必须知道几条内部事实才能用对？超过 3 条 → 接口太宽，把事实收进实现。
3. **接缝**：能否不改调用方就替换实现（替身 / 另一实现 / 另一宿主）？不能 → 先划接缝再拆任务；`.agents/commands/stages.md` Build §3 的 frontier 并行派发依赖它。
4. **杠杆**：这处改动是否让多个消费方同时受益？只有一个消费方且未来也不会有 → 不建抽象（AGENTS.md 最小改动 / YAGNI）。

## 步骤

1. **画现状**：列出候选模块的调用方与被调方（`grep` 引用即可），标出泄漏的内部事实。
2. **标浅模块**：用判据 1、2 找出直通层与宽接口，写清「删掉会怎样」。
3. **给 2 个候选形状**：接口签名 + 谁藏什么 + 接缝在哪；禁只给一个方案然后说「显然更好」。
4. **打分比选**：四条判据逐条给结论与证据，落 spec「方案对照表（取舍 + 建议）」。
5. **分叉定不了**：推理定不了且分叉真实（契约形状 / 数据流 / 性能取舍）→ 走 `arena`（2 路封顶，只读仓库，产物落对话或 `tmp/`）。
6. **落改动面**：选定的形状写进 spec「系统改动」与 plan 改动面；接缝位置写进任务拆解的依赖行。

## 本仓落点

- 装载点：`.agents/commands/new-task.md` §1c（Design 按需）。
- 复核：`review-method` Standards 轴的坏味道走查（Feature Envy / Shotgun Surgery / Primitive Obsession）与本技能判据同源，结论落评审清单，不在此下合入定性。
- 单源：比选前先确认「这个事实现在写在哪几处」——目标项目的口径单源是根 / 目录级 `AGENTS.md` 与 `.agents/config/policy.json`，同一事实出现第二处即按 papercut 登记，不靠新增一层去掩盖。

## 边界

- 深化不等于重写：优先把泄漏收进一个既有模块，而不是新增一层。
- 不给合入定性（`review-method` / 用户）、不做实现（`implementer`）、不回答「为什么长这样」（`why`）。
