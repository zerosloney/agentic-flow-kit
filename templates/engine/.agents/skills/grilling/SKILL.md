# grilling — 把诉求问到可判定

## 触发

- Plan 章立 intent 前：背景 / 目标 / 非目标还停在「大概想要」。
- Design 章起 spec 前：歧义清单 6 维填不出结论，或方案需要压力测试。
- 用户说「拷问我 / grill 一下 / 这个想法靠谱吗」。

## 核心

**一次只问一个问题，拿到回答再问下一个。** 批量问卷会把判断责任推回用户，且答案无法逐条落依据。

**先查后问。** 能跑出来 / 查出来的（行为、时序、布局、输出、存量数据、eval 可区分）先原型、查库、跑 eval，禁停下来问（口径单源 `.agents/commands/new-task.md` §1 提问分型）。只有产品取舍与偏好判断才升级为问询。可实验不豁免红线。

**问不可逆的那一侧。** 优先级：数据口径与身份 → 契约形状 → 失败路径 → 存量数据迁移 → 验收可测性。这五类问错了要返工，文案问错了只改一行。

## 步骤

1. **检索既有答案**：`flow-kit run kb-search.mjs "<关键词>" --scope workflow --type intents,specs,incidents` + `wiki/INDEX.md` + `workflow/glossary.md`。命中即引用，不重复问。
2. **列待决**：把诉求拆成可判定问句（答案能写成「是/否」或一个具体口径），按上面优先级排序。
3. **逐个问**：一轮一个问题，附上「为什么这条不可逆」与已知证据；用户回答后立刻复述成可判定条目请其确认。
4. **落文档不落对话**：答案回填 intent 六节 / spec「歧义清单」（列序 `维度 | 结论 | 依据 | 状态`），依据须可指认（节号 / `path:line` / 查库结果 / 实验输出）。
5. **分流沉淀**：术语分歧 → `domain-modeling` 记 `workflow/glossary.md`；不可逆取舍 → 记 `workflow/adr/`；推断类结论 → spec「假设与推断」。
6. **收口**：待澄清归零才进确认门。上界沿用 spec 口径：每维 ≤2 行、合计 ≤12、单轮问询 ≤5（`.agents/commands/stages.md` Design §2）。

## 输出格式

- **已判定**：条目 + 依据指针（可直接回填文档）。
- **待澄清**：还剩哪几条、为什么必须用户定。
- **已实验**：跑过什么、结论是什么（替代问询的那部分）。

## 本仓落点

- 装载点：`.agents/commands/new-task.md` §1c（Plan / Design 进入即装载）。
- 确认门：`confirm-doc.mjs` 对「待澄清 ≠ 0 / 依据空 / 缺维」直接拒；拷问没做完就落态会被挡回。
- 前提质询：解读性前提（如「展示诉求 vs 存储改写」）走 spec「前提质询」表，逐条反问对立解读——拷问负责问出来，质询门负责拦住自信的想错。

## 边界

- 只读检索 + 对话 + 回填文档；不改代码、不替用户拍板、不推进状态。
- 用户答「你定」→ 记为授权推断写进「假设与推断」，不写成已确认。
- 不做方案比选（`arena`）、不做接口形状评估（`codebase-design`）、不做实现（`implementer` 角色）。
