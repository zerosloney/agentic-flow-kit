# 机制使用量台账 (Mechanism Usage Registry)

> 门禁棘轮的出口：每个门禁机制的「触发统计口径 + 退役阈值 + 状态」单源登记于此。
> **台账的目的不是记录而是强制处置**：新增门禁机制须登记一行（一进一出，并点名它替代/合并的
> 既有机制，无替代则说明增量理由）；机制退役时状态改「已退役」并在最近触发列留档；
> 低频机制按退役阈值降级。
> 列序固定：机制 | 门禁位置 | 触发统计口径 | 退役阈值 | 最近触发 | 状态 | 处置期限。
> 本表归装户自持运营（sync 永不覆盖，同 metric-claims.txt 口径）；kit 引擎做 WARN 级格式校验
> （check-loop 检查 22：列数 / 状态枚举 / 待退役处置期限——advisory 不阻断，永不 hard），
> 对账纪律靠下方「维护纪律」人工执行；判定数据面由 check-loop 每次真实运行自动落账到
> `.agents/judgments.jsonl`（judgment-ledger，本地 gitignore），月度聚合经 agg-judgments.mjs 查账。

## 维护纪律

- **一进一出**：新增门禁机制必须同时在本表登记，并点名它替代/合并的既有机制（无替代则说明增量理由）。
- **月度对账**：每月初按「触发统计口径」列刷新计数（半自动：`node .agents/scripts/agg-judgments.mjs`
  查判定流水 `.agents/judgments.jsonl`——check-loop 每次真实运行自动落账，替代人工 grep 输出；
  git log 统计口径不变）；达到阈值的行改「待退役」并填处置期限。
- **数据面机制的「现役」≠「有数据」**：复核效果台账 / 评审黄金集校准类数据面机制登记后，月度对账须区分两件事：① 资产是否存在（建账即存在）；② 本月是否产生数据并写进留痕面——未产生 → 该月记「无跑数」，连续 6 个**有数据月**零记录才走退役阈值，缺月不算零命中（**年轻遥测不得制造假候选**，口径同 `agg-judgments --retire-candidates`）。
- **退役动作**：状态改「已退役」当日删除机制代码 + 其测试 + 本表更新，同一提交完成（不留死代码）。
- **模型代际触发**：每个机制都是对当前模型能力边界的假设（外部实证：harness 组件随模型代际逐件移动），既有退役阈值只有使用维度、缺代际维度——主力模型**代际变更**（主版本号或模型家族更换，如 GLM-4.x → 5.x；小版本/推理档变更不算）后的**下一次月度对账**须按下面分组逐件重评去留，结论写各机制「最近触发」列；重评本身不改状态列（退役仍走既有阈值）。首次对账时把本表现有机制按下组归类（此后新增机制在登记时即注明组别；本节用列表不用表格——防管道行被误当机制行解析）：
  - **A · 纪律假设**（假设：无机器检查时模型会跳步/声称未做之事，如配对完整性、留痕、占位符残留类检查）——重评动作：观察新代际下 WARN/hard 是否加速归零（是 → 按既有退役阈值自然走）；**不因代际主动拆门**——判据已机器化、边际成本 ≈ 0，拆门收益低于一次漏拦。
  - **B · 能力边界假设**（假设：机制强度绑在当前模型能力短板上，代际升级后假设可能失效，**须主动重评**，如常驻面体积预算、复核上下文独立性、判低逃逸类检查）——只重定阈值不轻拆门；其中信任边界/安全主干（凭据扫描、确认防伪类）**代际不撤门**，只重评执行成本。
  - **C · 机器判据**（纯确定性检查，与模型能力无关——格式/枚举/漂移/同步类）——代际免评。
  - **D · 宿主生态**（跟宿主软件版本走，不跟模型代际；宿主升级时随 Adapter 检查顺带过）。
  - **E · 测量自举**（数据面，代际只影响测量结论的解释、不改机制本身；跨代际比较月度指标先读委派/复核台账的模型代际基线注）——如门禁耗时、复核效果台账、退役催办。
