# 非工程角色：写一份 intent

> 目标：产品 / 业务 / 运营不需要 git 或命令行，也能产出下一阶段能直接读的 `intent.md`。
> 产出的文件仍以仓库为真相源；本文只负责“怎么进来”。

## 最简路径（claude.ai / Cowork）

1. 在会话里用自己的话描述：**谁遇到了什么问题、现在不能做什么、什么算变好、什么不在范围内**。不需要正式格式。
2. 让 Claude 按下面模板写成 `intent.md`；它会补问范围、用户、约束、成功判据。
3. 你逐条纠正它理解错的地方。**作者与时间**必须保留。
4. 让 Claude 通过 GitHub 连接器把文件提交到仓库的 `workflow/intents/<英文-kebab>.md`。
   不会 git 也没关系：连接器负责提交；你只需要确认文件名与内容。
5. 产品 owner 在仓库里把状态从 `draft` 改为 `approved`（或打回）。

## 模板

```md
# Intent: <一句话标题>
Author: <姓名/角色>  Status: draft
Date: <YYYY-MM-DD>

## 问题
<谁、在什么场景、现在不能做什么；有数字更好>

## 期望结果
<可观察的“变好”是什么>

## 受影响的人与系统
<用户/岗位/模块/接口>

## 约束
<不能新增 PII、必须复用现有认证、上线窗口……>

## 非目标
<明确不做什么，防止范围蔓延>

## 开放问题
<需要谁拍板；没有写“无”>
```

## 红线

- 不写实现方案（那是 spec/plan 的事）；只写要什么、为什么、约束。
- 不在 intent 里贴密钥、真实用户数据或内部链接凭据。
- 状态只能由产品 owner 改；agent 不自行把 draft 改成 approved。
- 一个 intent 只解决一个问题；拆得开就拆。

## 技术侧配合

- 仓库里跑 `flow-kit run fill-intent.mjs` 可生成骨架（有引擎时）。
- 进入 Design 前，产品 owner 必须回答 open questions 或明确“带问进入”。
