- **特别之处**：本锚比 frontmatter 日期更「顺手可写」——文件名的 `YYYY-MM-DD-` 前缀是项目命名规范的**强制组成部分**，作者每次建档都在写它；而改 frontmatter 日期需刻意为之

## 根因
**生效日锚取自可手填的字段，且该字段恰是日常必写的命名前缀。**

判据为 `filedate = base.slice(0, 10)`（文件名前 10 字符）→ `isNew = filedate >= accCutoff`。它把「这条规则是否已对本文档生效」的决定权交给了文件名——而文件名日期由作者自由填写，且**写早没有任何代价**。

深层原因同前两单：**用可手填的自报字段判断"该不该受管"，等于把门是否生效的决定权交给被门约束的对象**。本处的自报字段恰好零成本（命名规范的一部分），故被触发的概率显著高于 frontmatter 日期。

## 为什么之前没拦住
- **门禁层**：检查 8 自己就是依赖该字段的门，自举循环无法自查；且**没有任何检查项审计「生效日锚是否可信」**
- **测试层**：既有场景全部用**非 git fixture** 构造（`mkfix()` 建临时目录后直接写文件），锚在测试里恒等于「文件名日期」——测试**只验证了"按文件名判定"这条实现路径可用**，从未验证「该锚能否达到目的」。这与上一单独立复核指出的模式同源：**用例在验证判据按设计工作，而非验证判据能否达到目的**

> **复核更正（P1，2026-09-28）**：本单立项时把该原则表述为「锚须取**不可手填**的事实」，并在 spec/README/代码注释中写成「通道已关闭」——**该表述不实**。实测：`%aI` 是 **author date（作者自报时间戳）**，`git commit --date=<过去>` 一条参数即可伪造 → 仍可静默放行（复核实证）。**准确的原则是「锚须取日常不可顺手改动的事实」**：它把绕过成本从「改个文件名（日常必写、零成本）」抬到「主动伪造时间戳」，后者与伪造台账同属本地信任边界内不可机器防。此处如实更正，不宣称通道已关闭。
