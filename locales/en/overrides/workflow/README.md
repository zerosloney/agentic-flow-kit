# workflow — AI-driven closed loop (single source of truth)

This directory is the sole home of the AI workflow engine. L1 new requirements enter through a single plan; L2/L3 new requirements go intent → spec → plan; fixes go through an incident. At the micro-task layer, a "Task Owner + AI paired closed loop" model is used, with confirmation completed in one sentence in the conversation (TTY / delegated auto-record). At the macro trunk layer, multi-person collaboration is supported; merges to main are guarded by the TFS PR branch policy (Peer Review team review + Azure Pipelines CI gates sourced from the same scripts as local), and traceability relies on git (commit + PR records + release tags).

> All new closed-loop records are written in this directory.

## Directory structure

| Directory | What goes here | Naming |
|------|--------|------|
| `intents/` | L2/L3 new requirement entry: background, goals/non-goals, acceptance criteria, level, red lines touched. Not created for L1 new requirements | `YYYY-MM-DD-<topic>.md` |
| `specs/` | L2/L3 design spec: functional behavior, data flow, system changes, constraint-compliance mapping. Not created for L1 | Same name as intent / incident |
| `plans/` | L1 new requirement entry (source / goals / red lines / change plan / constraints and risks / verification plan / acceptance criteria). L2/L3 and fixes still share the name of intent / incident | `YYYY-MM-DD-<topic>.md` |
| `incidents/` | Incident retrospective: timeline, root cause, why it was not caught, retrospective triad | `YYYY-MM-DD-<topic>.md` |

**Naming is always English kebab-case** (e.g. `2026-09-07-supplier-rating-field.md`), **Chinese file names are forbidden**—the original check-loop §9 non-ASCII filename warning retired with the 2026-10-28 engine slimming; the naming convention is unchanged. Document content (title/body) is not subject to this restriction.

**Document protocol (structured 2026-09-13)**: the header of all four document types is YAML frontmatter (restricted subset, one `key: value` per line, the single source of check-loop machine fields)—`状态` (intent/spec/plan: draft/approved/done/superseded/cancelled; incident: open/fixed/closed, **strict enum**, notes go in the `备注:` key), `级别` (L1/L2/L3), `日期`/`发现` (YYYY-MM-DD), `模块` (**required for new documents since 2026-09-22**, values from the `.agents/config/workflow-modules.txt` vocabulary, a single value uses the dominant module; existing documents are not backfilled, AI fills them in when touching), L3 spec's `确认结果`/`确认时间`, backfilled documents `流程: legacy`. **`日期` fallback rule (fixed 2026-10-27)**: plans are generated by `fill-plan.mjs` and `plans/_TEMPLATE.md`; **frontmatter has written `日期` since 2026-10-27** (previously renderPlan accepted a date parameter but did not persist it)—for any gate whose precondition is frontmatter `日期` (delegation ledger presence gate; check 18 retired with the 2026-10-28 engine slimming), when the date is missing it still **falls back to the filename prefix** `YYYY-MM-DD` as a second safety net (following check 15's existing rule; check 19 retired); if neither frontmatter nor filename has a date → undecidable → skip. The old rule "no date means skip the whole section" silently disabled the delegation gate for most L2/L3 plans (after 52 anchors, L2/L3 terminal documents were never reconciled). **`状态` transitions must pass through `approved`** (the machine-visible state of confirmation; `done` appears only at close): for specs/plans created since 2026-09-23, if already done and git history never contains a line-start `状态: approved`, check-loop reports a "confirmation state missing" warning. check-loop scans only frontmatter for machine fields (`fm_get` field assertion); the body no longer writes "状态：/级别：" lines; narrative fields (independent review / retrospective triad / acceptance checks) remain in the body anchored by section. Protocol changes and backfill migration are in the 2026-09-13 `docs(workflow)` commit. **Explicit blocking of ambiguities (2026-10-16, NEEDS-CLARIFICATION marker)**: when drafting or revising a spec/plan and an ambiguity cannot be decided alone (multiple interpretations / missing standard / external fact dependency), **guessing is forbidden**—insert `[NEEDS CLARIFICATION]: <one-line question>` in place to ask the user; after clarification remove the marker and record the decision in the body; the marker must be cleared before advancing to approved (self-check discipline; grep the marker in active documents for the pending-clarification list. Automated cross-artifact gap checks are deferred—the conflict with the "defer new gates" trade-off is explicitly logged, to be revisited after D6 metrics). **Commitment-surface binding (new 2026-10-27)**: what the user approves at the moment of `approved` is the **commitment surface** (criteria text / red lines / goals / change plan / constraints and risks)—a commitment rewritten after confirmation without re-approval = the user did not approve what is delivered at close. Legal actions at close (ticking acceptance + evidence backfill, `确认结果`/`确认时间` backfill, review-line re-anchoring) **do not change the commitment surface** and are not false-flagged after normalization; if commitment criteria are rewritten, hard block (check 15) + rejection at close (confirm-doc commitment-surface binding gate). The **only way** to change a commitment = after the user re-approves, run `confirm-doc <doc> --reconfirm --delegated "<original words>"` to re-record the commitment-surface fingerprint (does not advance status; the status line is still written by confirm-doc, do not hand-edit frontmatter); existing records (pre-launch confirmations, ledger rows without a `commit` field) are not retroactive. **Editing a closed document body requires re-recording the fingerprint in the same commit (2026-11-10, incident 2026-10-26-workflow-confirmation-drift-hard-block)**: editing the body of a closed (done/superseded/closed/cancelled/fixed) document = must re-record the confirmation fingerprint in the same commit (`confirm-doc` / `--reconfirm`) or use a compensation row (`append-compensation.mjs`), otherwise check-loop flags "confirmation content drift"; at commit time `check-doc-body-drift.mjs` provides advisory visibility (not a gate).

Each subdirectory's `_TEMPLATE.md` is a starter template; copy it and fill it in; do not edit the template itself.

The root `regression-checklist.md` is a **living regression checklist**: the unified landing point for deploy must-pass items and incident anti-recurrence verification, extended as modules ship and appended as incidents occur.

**The three append-only ledgers are sharded** (2026-10-13 ledger-shard-ledgers): data rows of `regression-checklist` / `delegations` / `papercuts` are stored monthly in `workflow/<ledger>.d/<YYYY-MM>.md`; the main ledger keeps only the description, table header and GENERATED area—eliminating the size and merge-conflict surface of "rewrite the whole file on every append". The single source for reads and writes = `flow-kit run ledger-shards` (the read side automatically merges the main ledger ∪ all shards; existing consumers need no change); append one row with `flow-kit run ledger-shards.mjs --append <ledger> --row "<row>"`. (The fourth ledger `deploy-observations` was retired and deleted with the deploy ritual—2026-10-29 owner decision: actual releases do not use a tag/24h observation ritual; merge = PR create → review → regression → merge → archive, see `deploy.md` header note.) confirmations.d shards start in 2026-10; 2026-09 has no shard (that month's confirmations are traceable only via git; historical gaps are not backfilled); jsonl ledger schemas self-describe by field presence across generations (e.g. quoteGrounding since 2026-10-24), with no version field (2026-11-05 decision).

**Gate judgment monthly shards** (2026-10-22 gate-metrics-shard): `workflow/gate-metrics.d/<YYYY-MM>.jsonl` holds one row per month (rule × WARN/BLOCK), generated by `flow-kit run agg-judgments.mjs --emit-month` and committed with the change; pre-push monthly checks automatically backfill the previous month's shard. The retirement criterion (N consecutive months = 0) reads the union of local `.agents/judgments.jsonl` and the shards and takes the max—machine/worktree changes no longer reset it to zero; multi-machine union (`.gitattributes` reuses `jsonl-union`).

**Claims ledger** (append-only, monthly): `workflow/claims.d/<YYYY-MM>.jsonl` records one sentence a future session might take as given, plus a quote that already exists in the repo. Append with `flow-kit run claims.mjs add`. `recheck` only reports whether that quote is still in the file. Its exit code is always 0. It is not a gate, and it does not rewrite past lines. Merges use `jsonl-union`.

## Usage

- **Start a new task**: run `.agents/commands/new-task.md` (leveling + L0 minimal path / L1 fast path entrance); L2/L3 enter the four chapters of `.agents/commands/stages.md` (Plan → Design → Build → Test, 2026-11-08 tier 2-F four-in-one)
- **Board (optional, not started by default)**: run `flow-kit run ensure-board.mjs` manually when needed (idempotent: liveness probe / auto-restart stale code / launch browser on fresh start), live read-only at http://127.0.0.1:8933; **advisory layer, not a gate; alert semantics aligned with check-loop hard blocks**. "Stale code" = LastWriteTime of `board/index.html` or `workflow-board-server.mjs` later than the board process start by 2s (restart if either is updated); if the port is occupied, probe `/api/board` first—a response without `cards` means another process, so leave it alone, do not kill, and skip to the next port
- **Search**: read `INDEX.md` for active workflow (generated; regenerate with `flow-kit run gen-workflow-index.mjs`, drift check with `--check`); cross-corpus search with `flow-kit run kb-search.mjs "<term>"` (workflow section-level location + wiki full text, filters `--type/--module/--status/-n`; `--status all` for an explicit full set)
- **Archive**: archive on close (2026-10-13 archive-on-close)—after `confirm-doc.mjs` records the terminal state it automatically `git mv`s **the family involved in this confirmation** (same-name intent/spec/plan/incident) into `workflow/archive/<terminal-month>/{type}/`, so active directories no longer accumulate terminal artifacts. **Feature branches are not archived by default** (since 2026-10-15, to prevent CI lane gates from blocking legitimate merges)—after merge, main/develop close or sweep takes over; staying within the 21-day window is normal. For historical backlog run `flow-kit run archive-sweep.mjs [--window 21] [--execute]` (dry-run by default) manually in batches; archived artifacts remain searchable by `kb-search` (`archive/<batch>/<type>` is covered), while check-loop pairing and content-binding gates scan only the four direct directories and do not trigger on archived items. When terminal artifacts pile up, run archive-sweep monthly (dry-run to inspect candidates, `--execute` to apply).
- **spec lifecycle stance (2026-10-16 owner decision, Böckeler three-layer classification: spec-anchored + long-term maintenance)**: a spec is a **continuously referenced source of truth and does not expire after delivery**—when a code change touches behavior covered by a spec (including archived ones), compare against that spec: behavior drift either changes the code back to the spec or changes the spec in the same commit; disputes go to an incident for adjudication. **Archiving is capacity management, not invalidation**: archiving only removes terminal artifacts from active scan surfaces (INDEX active rows / check-loop four-directory scan / monthly regeneration); source-of-truth status and revision rights are unchanged—archived specs can be revised in place without changing the archive location. Size governance observes before setting limits: spec line count / acceptance item distribution is collected in the metrics.md observation column (advisory caps conflict with the "defer new gates" trade-off; explicitly postponed until D6 metrics are complete).
- **Follow-up on the same feature (search before create, 2026-10-22)**: before starting work, search `workflow/specs/`, `workflow/archive/**/specs/`, `.agents/skills/verify-ui/features/`, `workflow/regression-checklist.md` by "module + feature keyword". If a hit covers the same behavior → revise the original (specs are revised in place per the item above; do not create new); create new only for a genuinely new feature. When creating task documents, include the feature key in the topic for later search.
- **Verification**: `.agents/commands/stages.md` Test chapter (static gates + UI testing); DB-switch liveness and API anti-recurrence assertions run via `node scripts/verify/business/regression-smoke.mjs` (read-only by default; `--writes` creates and cleans its own probes, dev DB only)
- **Review**: `.agents/commands/review.md` (P0 / P1 / P2 grading: machine baseline + AI self-check list, user decides classification and merge)
- **PR panel review**: the panel has been retired to a **manual tool** (2026-11-09 automatic gate retired)—pre-push / CI / pr-create no longer enforce a review ledger; orchestrate manually per `.agents/commands/pr-review.md` when needed; create a PR via `flow-kit run pr-create.mjs ...` (gate first, then call `tfs-pr create`)
- **Deploy**: `.agents/commands/deploy.md` (must-run checklist before release)
- **Quantification**: delegated/self-done results go in `delegations.md`, aggregate with `flow-kit run agg-delegations.mjs` (**the concurrency expansion threshold is in that file—do not expand concurrency before the numbers qualify**); the **monthly snapshot** of corpus and resident-surface size runs `flow-kit run gen-workflow-metrics.mjs` (one row per month in `metrics.md`, rerunning in the same month updates it; details on stdout)
- **Traceability**: git is the audit trail. Two driving paths, choose one and never mix—manual stage routing (confirmed workflow documents folded into one `docs(workflow)` commit, code in a separate commit; ordinary L1 requirements have only a plan, fixes have incident+plan, L2/L3 have entry+spec+plan) or the `pipeline-run` state machine (per-stage `docsCommit` commits of the same shape; protocol single source `.agents/commands/pipeline-run.md`). Release does not use a tag/24h observation ritual (release tag and release observation ledger retired 2026-10-29). Local development relies on the Independent Reviewer for cognitive-isolation self-check; main merges get complete audit evidence through TFS PR team review and git history
- **Levels**: L1 implementation-level (does not hit L2/L3; the entrance for new requirements is a plan) | L2 rules / contracts (coding authority / shared contracts / existing interface semantics / global cross-cutting rules, closed set of touch surfaces in `.agents/commands/new-task.md`) | L3 data and runtime structure (schema / migration SQL / DI chain / auth and middleware pipeline). Mixed changes take the higher level

## Execution model

- The default host main agent handles stage routing, user confirmation, key judgment and final acceptance; it is not registered as an extra role.
- Stage commands delegate to `.agents/roles/implementer.md`, `.agents/roles/independent-reviewer.md`, `.agents/roles/ui-verifier.md` only when boundaries are explicit.
- OpenCode, Trae and ZCode register roles through thin adapters under `.opencode/agents/`, `.trae/agents/`, `.zcode/agents/`; role behavior is maintained only in `.agents/roles/`.
- PI registers 7 role shells through `.pi/agents/` (same contract as `.agents/roles/`); `.pi/extensions/` wires tool_call to the two gates under `.agents/hooks/`, with a single judgment source and no duplication. `.pi/` is a machine-private directory (`.gitignore`) and is not propagated by clones; stage commands follow the root `AGENTS.md` §4 routing table and are read directly by the main Agent from `.agents/commands/*.md` (pi has no wf-* command shells); the wiring reality is reconciled by `check-local-gates.mjs` advisory, mechanism in `runtime-env.md` §6.4.
- Cline connects through `.cline/workflows/` (7 pointer shells → `.agents/commands/`) and `.cline/agents/` (7 role definitions, **YAML** → `.agents/roles/`); Cline natively reads `AGENTS.md` and `.agents/skills/`, so the rule and skill surfaces take effect with zero changes. `.cline/` is a machine-private directory (`.gitignore`) and is not propagated by clones; **the two gates are not wired** (the Cline hook protocol is incompatible with the repo's `.agents/hooks/*.cjs`; integration needs a protocol adapter), mechanism in `runtime-env.md` §6.4.
- When the host does not support subagents, execute according to the command frontmatter `fallback`; but **independent review has no fallback**—the L2 / L3 `independent-reviewer` is always `required: true`; if the host does not support subagents, open a new session and never fall back to self-check by the original main agent.
- Subagents must not cross user confirmation gates, nor commit, merge or deploy on their own; all results are reviewed by the main agent before user decision.

## Closed-loop rules

1. L1 new requirements start from an approved plan, with no separate intent. L2/L3 new requirements start from an approved intent. Fixes start from an approved incident; L1 fixes create a same-name L1 plan and use `.agents/commands/new-task.md` §L1 fast path (normally do not open `stages.md`)
2. L2/L3 must first have a same-name spec approved (L2/L3 always force independent review, see `stages.md` Design §3) before drafting a plan. L1 plans are drafted and confirmed in `new-task.md` §L1 fast path (`stages.md` covers only L2/L3); the sections are entry / change plan / constraints and risks / verification plan / acceptance criteria
3. Implementation artifacts must pass static gates (architecture red lines + build + test)
4. Production / live-test defects fall back to `incidents/`; the retrospective triad (new intent, anti-recurrence verification, standards entry) is mandatory; **when the root cause is "gate missing / standard not implemented / systemic problem", a new intent must be filed even if the structural fix is complete**, to track systemic improvement; do not bypass the intent loop on the grounds that "the fix is already done"
5. Close in test, regardless of whether it has reached prod. L1 ticks the plan's "Acceptance criteria" and adds evidence, then plan → done. L2/L3 tick the intent's "Acceptance criteria", then intent → done and the same-name plan becomes done. Fix incidents go open → fixed → closed and the same-name plan becomes done. If done still has unchecked items, check-loop blocks (hard-block for documents created since 2026-09-12; existing documents are only warned, not backfilled). Going to prod follows deploy separately (PR merge checklist, no tag/24h ritual)
6. Abandonment records: approved but not done → `superseded`; cancelled before completion → `cancelled`. Both are confirmed terminal states, and check-loop does not block on "status unconfirmed"; L3 abandoned documents are exempt from "confirmation result must be approved"
7. Subsequent regression checklists and weekly checklists are also archived in this directory
8. **Check 17 (release draft gate) was retired and its code deleted on 2026-10-21**: this repo root `package.json` has no `version` field, so the version anchor condition never holds (2026-10-06 audit); releases do not use the tag ritual (see "Traceability"). That hard gate no longer exists; do not interpret it as "always skipped"
